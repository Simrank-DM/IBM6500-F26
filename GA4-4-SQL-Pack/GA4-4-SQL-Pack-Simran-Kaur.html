Purpose and dataset

This SQL pack uses eight GoogleSQL queries to practice working with GA4 export data. My focus is on keeping the SQL readable and separating events, observed users, and sessions so the results have a clear meaning.

Dataset: bigquery-public-data.ga4_obfuscated_sample_ecommerce.events_*
Analysis period: January 1–31, 2021, inclusive. Every base-table read uses a constant _TABLE_SUFFIX range to scope daily export tables. Dates summarized from event_date follow the property’s reporting date; Query 1 displays timestamps in UTC.

The public Google Merchandise Store sample covers November 2020 through January 2021. It is obfuscated, can contain placeholders, and is different from the live GA4 demo account (Google sample documentation). These examples demonstrate transferable skills for later team analysis; they do not measure TBFI website activity.

Validation status: SQL has been reviewed against Google’s documented export schema but has not been executed in BigQuery. No numeric results or business findings are claimed. The SQL blocks are displayed as source code and do not run when this report renders.

Eight GoogleSQL queries

Query 1: Inspect recent purchase events

SELECT
  event_date,
  TIMESTAMP_MICROS(event_timestamp) AS event_time_utc,
  user_pseudo_id,
  ecommerce.transaction_id
FROM `bigquery-public-data.ga4_obfuscated_sample_ecommerce.events_*`
WHERE _TABLE_SUFFIX BETWEEN '20210101' AND '20210131'
  AND event_name = 'purchase'
ORDER BY event_timestamp DESC, user_pseudo_id
LIMIT 50;

This query returns up to 50 of the latest purchase-event records in January 2021. I would use it to inspect timestamps and transaction IDs before building a purchase summary. Each row is an event record, so repeated purchase tracking can produce multiple records for one order; LIMIT restricts the output, while the table-suffix filter restricts the scanned dates.

Query 2: Daily events and observed users

SELECT
  PARSE_DATE('%Y%m%d', event_date) AS activity_date,
  COUNT(*) AS event_count,
  COUNT(DISTINCT user_pseudo_id) AS observed_users
FROM `bigquery-public-data.ga4_obfuscated_sample_ecommerce.events_*`
WHERE _TABLE_SUFFIX BETWEEN '20210101' AND '20210131'
GROUP BY activity_date
ORDER BY activity_date;

This query summarizes event volume and distinct observed user identifiers for each day. I would use the output to spot unusual traffic changes and decide which dates need closer review. Event counts measure recorded activity, while observed users are distinct non-null browser/device identifiers rather than verified people; daily user counts should not be added to obtain monthly unique users.

Query 3: Page views by device category

SELECT
  device.category AS device_category,
  COUNT(*) AS page_views,
  COUNT(DISTINCT user_pseudo_id) AS observed_viewers
FROM `bigquery-public-data.ga4_obfuscated_sample_ecommerce.events_*`
WHERE _TABLE_SUFFIX BETWEEN '20210101' AND '20210131'
  AND event_name = 'page_view'
GROUP BY device_category
ORDER BY page_views DESC;

This query compares page-view volume and distinct viewers across device categories. I would use it to prioritize which device experience to inspect first. A person can appear on multiple devices, and a high page-view count alone does not establish better engagement or conversion.

Query 4: Top page URLs with string parameters

WITH page_events AS (
  SELECT
    user_pseudo_id,
    (SELECT ep.value.string_value
     FROM UNNEST(event_params) AS ep
     WHERE ep.key = 'page_location') AS page_location
  FROM `bigquery-public-data.ga4_obfuscated_sample_ecommerce.events_*`
  WHERE _TABLE_SUFFIX BETWEEN '20210101' AND '20210131'
    AND event_name = 'page_view'
)
SELECT
  page_location,
  COUNT(*) AS page_views,
  COUNT(DISTINCT user_pseudo_id) AS observed_viewers
FROM page_events
WHERE page_location IS NOT NULL
GROUP BY page_location
ORDER BY page_views DESC, page_location
LIMIT 20;

This query extracts page_location from its string field and ranks the 20 most-viewed full URLs. I would use the output to identify pages that deserve a content or navigation review. Missing URLs are excluded and query strings can split one page into several URLs; the scalar extraction assumes each event has no more than one matching key.

Query 5: Count observed sessions using integer parameters

WITH extracted AS (
  SELECT
    user_pseudo_id,
    (SELECT ep.value.int_value
     FROM UNNEST(event_params) AS ep
     WHERE ep.key = 'ga_session_id') AS ga_session_id
  FROM `bigquery-public-data.ga4_obfuscated_sample_ecommerce.events_*`
  WHERE _TABLE_SUFFIX BETWEEN '20210101' AND '20210131'
), sessions AS (
  SELECT user_pseudo_id, ga_session_id
  FROM extracted
  WHERE user_pseudo_id IS NOT NULL
    AND ga_session_id IS NOT NULL
  GROUP BY user_pseudo_id, ga_session_id
)
SELECT COUNT(*) AS observed_sessions
FROM sessions;

This query extracts the integer ga_session_id and counts distinct user-and-session pairs observed during January. I would use it when I need a session denominator instead of treating events as sessions. A session ID alone is not unique across users, so both fields are required; missing identifiers are excluded and sessions crossing the date boundary are only partly observed. The result is an observed-session count, not a claim that it matches the GA4 interface.

Query 6: Inspect numeric purchase values by currency

WITH purchase_values AS (
  SELECT
    (SELECT ep.value.string_value
     FROM UNNEST(event_params) AS ep
     WHERE ep.key = 'currency') AS currency,
    (SELECT COALESCE(ep.value.double_value,
                     CAST(ep.value.int_value AS FLOAT64))
     FROM UNNEST(event_params) AS ep
     WHERE ep.key = 'value') AS purchase_value
  FROM `bigquery-public-data.ga4_obfuscated_sample_ecommerce.events_*`
  WHERE _TABLE_SUFFIX BETWEEN '20210101' AND '20210131'
    AND event_name = 'purchase'
)
SELECT
  currency,
  COUNT(*) AS purchase_events,
  COUNT(purchase_value) AS events_with_numeric_value,
  SUM(purchase_value) AS reported_purchase_value,
  AVG(purchase_value) AS avg_value_per_valued_event
FROM purchase_values
GROUP BY currency
ORDER BY purchase_events DESC;

This query extracts currency as a string and value as a double, with an integer fallback, then summarizes purchase-event values separately by currency. I would use it to check value coverage before reporting monetary totals. SUM and AVG ignore missing values, and a null currency group means the currency was not supplied. These are reported event values, not deduplicated order revenue or net revenue after refunds; currencies must not be added together.

Query 7: Audit page-view parameter coverage

WITH parameter_audit AS (
  SELECT
    (SELECT COUNTIF(ep.key = 'page_location')
     FROM UNNEST(event_params) AS ep) AS location_key_count,
    (SELECT COUNTIF(ep.key = 'page_location'
                    AND ep.value.string_value IS NOT NULL
                    AND ep.value.string_value != '')
     FROM UNNEST(event_params) AS ep) AS usable_location_count
  FROM `bigquery-public-data.ga4_obfuscated_sample_ecommerce.events_*`
  WHERE _TABLE_SUFFIX BETWEEN '20210101' AND '20210131'
    AND event_name = 'page_view'
)
SELECT
  COUNT(*) AS page_view_events,
  COUNTIF(location_key_count = 0) AS events_missing_key,
  COUNTIF(location_key_count > 1) AS events_with_duplicate_key,
  COUNTIF(usable_location_count > 0) AS events_with_usable_url,
  ROUND(100.0 * SAFE_DIVIDE(
    COUNTIF(usable_location_count > 0), COUNT(*)), 2)
    AS usable_url_pct
FROM parameter_audit;

This query checks whether page-view events contain a usable page_location string and flags duplicate keys. I would use it to assess whether the top-page query is leaving out a meaningful share of page views. The percentage is based on events, and a nonempty URL is not proof that the URL is correct; duplicate matching keys should be investigated before using scalar extraction.

Query 8: Join daily traffic and purchase summaries

WITH base AS (
  SELECT event_date, event_name
  FROM `bigquery-public-data.ga4_obfuscated_sample_ecommerce.events_*`
  WHERE _TABLE_SUFFIX BETWEEN '20210101' AND '20210131'
), daily_events AS (
  SELECT event_date, COUNT(*) AS total_events
  FROM base
  GROUP BY event_date
), daily_purchases AS (
  SELECT event_date, COUNT(*) AS purchase_events
  FROM base
  WHERE event_name = 'purchase'
  GROUP BY event_date
)
SELECT
  PARSE_DATE('%Y%m%d', d.event_date) AS activity_date,
  d.total_events,
  COALESCE(p.purchase_events, 0) AS purchase_events,
  ROUND(100.0 * SAFE_DIVIDE(
    COALESCE(p.purchase_events, 0), d.total_events), 2)
    AS purchase_event_share_pct
FROM daily_events AS d
LEFT JOIN daily_purchases AS p
  ON d.event_date = p.event_date
ORDER BY activity_date;

This query joins two daily summaries and calculates purchase events as a percentage of all recorded events. I would use it to monitor how the mix of recorded activity changes across days; the left join retains traffic days with zero purchase events. Both sides have one row per date, which avoids multiplying event rows during the join. This is purchase-event share, not a user or session conversion rate, and it can change when other event tracking changes.

Notes for reuse and validation

  1. Open BigQuery with GoogleSQL enabled and use the US processing location for the public sample. Paste and run each query separately, checking the estimated bytes before execution.
  2. Confirm the output columns and metric definitions above. Save actual result evidence before describing findings; an empty output is not automatically a SQL error.
  3. Inspect Query 7 for missing and duplicate page-location keys. Queries 4–6 assume their selected parameter keys are unique within an event; check the corresponding keys if adapting the queries to another property.
  4. To reuse the code with team data, replace the table path and date bounds in every query. Check which events and parameters actually exist before substituting form or lead events.

Parameter types: Use string_value for text, int_value for integers, and double_value for double values. The field selected must match how the parameter was exported; a key can exist while the selected typed field is null (GA4 export schema).

Learning reflection

The most useful part of this pack for me is seeing why the counting unit matters. Counting events is straightforward, but counting sessions requires extracting a parameter and combining it with the user identifier. I also understand why I need to check missing parameters and summarize each table before joining. These are the patterns I want to use when helping with the team’s BigQuery work.
